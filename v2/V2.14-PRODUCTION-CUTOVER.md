# HeliLog V2.14 — Production cutover preparation

**Status: RELEASE CANDIDATE PREPARATION ONLY.** Nothing in this document authorizes a public launch, transfer of pilot data or change to V1 production. HeliLog has not been independently certified as an EASA-compliant electronic logbook.

## Verified current topology
- V1 stable: \`main\` → Render \`helilog-pwa\`, publish directory \`.\` → \`https://helilog-pwa.onrender.com/\`.
- Archived V1 fallback: Git branch \`archive/v1.43.2\` (commit \`72aad71e103044d35a71315dd8341c72aa7b05ac\`).
- V2 staging: \`v2/development\` → Render \`helilog-v2-test\`, publish directory \`v2\` → \`https://helilog-v2-test.onrender.com/\`.

- V2 has passed user-reported 22/22 two-account acceptance checks, cross-account SQL/RPC isolation probes and two independently downloaded encrypted recovery drills. These do not constitute a complete security or recovery audit.

## Completed with V2.14
- \`scripts/build-helilog-production.cjs\` builds a minimal, root-path static package in \`dist-prod\` while preserving source files, Git branches and existing user data.
- The candidate packager refuses to run without a manual release gate; requires HTTPS origins and an independent production Supabase project; refuses the test backend, test/staging site, non-publishable key, missing assets, and unsafe output paths.
- Candidate cloud auth accepts \`environment:"production"\` **only** when the running website origin exactly matches the packaged \`productionOrigin\`; staging still accepts \`environment:"test"\` for the existing test site.
- Production-candidate manifest, PWA cache and account sign-in label are distinct from TEST builds. Do not remove the local Test Mode warnings or claim EASA approval.
- GitHub Actions runs packaging/regression tests with **fictional credentials only**, never a real production publishable key.

## Blockers — do not switch the production service until complete
1. **Provision the production Supabase project** only after the owner selects the organization and confirms the provider's quoted cost (if nonzero). Keep it separate from test data and do not copy any test flight, archive, signature or user account automatically.
2. **Review and apply DB migrations** on the fresh production project: \`helilog_v22_foundation\`, \`helilog_v24_complete_record_sync_and_archives\`, \`helilog_v282_pending_flight_correction_proposals\`, \`helilog_v29_private_daily_snapshots_and_restore\`, \`helilog_v29_no_correction_draft_resurrection\`, \`helilog_v210_backup_health_retention\`, and \`helilog_v212_trigger_execution_hardening\`. Verify RLS, RPC grants and all expected functions. Plan an independent, securely stored encrypted backup and a full disaster-recovery test.
3. **Configure Auth:** invite-only onboarding enforced by Supabase (disable public signup), site URL and reset redirect \`https://helilog-pwa.onrender.com/?helilog_recovery=1\`, email template, verified SMTP, rate limits, password policy and leaked-password protection (if available). Test with at least two new fictional production accounts and reset password end-to-end.
4. **Security:** all seven authorized \`SECURITY DEFINER\` archive/backup functions are designed for authenticated requests, but remain visible in the Supabase Security Advisor; document approved grants and independently re-test cross-account ownership in the new project. Never revoke the seven required RPCs without a replacement.
5. **Regulatory and privacy:** publish a clear private beta notice and data-processing/privacy information, covering medical records and signatures, retention, requests for account deletion, incident response, and explicit disclaimer that HeliLog is not an EASA-certified logbook.
6. **V1 migration:** V1 previously used browser-local storage. Before cutover, document a read-only/export route and verify backups for any users who still depend on that origin. Do not overwrite, auto-import or delete V1 device-local data.
7. **Release candidate verification:** dry-run the candidate build, test root-path PWA install/offline cache, login, logout, archive immutability, backups, encrypted recovery and real email links on an **isolated preview origin**, without exposing real records. Check test data cannot leak into the production project.

## Manual candidate packaging (never run from the V1 production site)
After selecting and provisioning a real separate production backend, the candidate package needs the following non-secret build-time values:

\`\`\`bash
HELILOG_RELEASE_GATE=prepare-only \
HELILOG_PROD_ORIGIN=https://helilog-pwa.onrender.com \
HELILOG_PROD_SUPABASE_URL=https://<PRODUCTION_PROJECT_REF>.supabase.co \
HELILOG_PROD_SUPABASE_PUBLISHABLE_KEY=sb_publishable_<PRODUCTION_PUBLIC_KEY> \
node scripts/build-helilog-production.cjs
\`\`\`

The script creates \`dist-prod/\` using only explicitly allowlisted static assets. The publishable key **is visible to website visitors** by design. Never provide a secret/service-role key or a database password.

When the candidate is approved and the exact final web origin has been tested, the **future** V1-to-V2 Render cutover would:
- Merge the verified, release-ready V2 changes into \`main\`, preserving \`archive/v1.43.2\`.
- Switch \`helilog-pwa\` build command to \`node scripts/build-helilog-production.cjs\` and publish directory to \`dist-prod\`, with the validated environment variables.
- Verify service worker behavior and Auth callbacks from the final origin. Observe Render deploy status, then manually confirm private account logins, logbooks, backups and archive integrity.
- Keep \`helilog-v2-test\` linked to \`v2/development\` and the existing test Supabase project for future feature iterations.

**Rollback:** revert production Render settings and stable branch to the known archived V1 revision. Do not roll back by deleting data, overwriting a cloud account or purging browser storage.
