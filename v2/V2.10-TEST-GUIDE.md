# HeliLog V2.10 — Backup Health and Isolated Recovery (TEST)

**Deployment target:** separate V2 test website. V1 production is never touched. Use fictional logbook data and signatures only.

## 1. Backup health and monitoring

1. Open **Profile → V2.10 Backup reliability & recovery** in a signed-in web browser.
2. Choose **Check backup health & retention**.
3. Confirm the latest backup time, scheduler state, verified snapshot checksum and recent failed-job count are displayed.
4. A healthy status means the most recent in-database snapshot is readable and passes its checksum, the schedule is enabled, and no failures were recorded in the last seven days. It **does not** certify an independently recoverable off-provider backup.
5. Test-mode scheduler: **03:00 UTC daily**, configured using PostgreSQL pg_cron. If scheduler is disabled, backup is older than 36 hours, checksum mismatches or recent job failures exist, the status will warn. Health is evaluated on request, **not pushed as an alert while the app is closed**.

## 2. Retention — planning, not deletion

The preview counts daily, manual, pre-restore snapshots and daily snapshots that would qualify for eventual pruning under this proposed rule:
- Retain the 90 most recent daily snapshots.
- Retain a monthly anchor within the last 12 months.
- Retain all manual and pre-restore snapshots.

**V2.10 deliberately deletes no backup snapshots.** Provider-independent recovery needs successful end-to-end validation before enabling deletion.

## 3. Encrypted offline recovery drill

1. Under Profile use **Refresh backup history**, choose a snapshot and **Download encrypted backup**. Save it separately from your laptop/device, using a strong passphrase.
2. Enter the passphrase under **V2.10 — Isolated encrypted recovery drill** and choose the saved encrypted JSON.
3. The client decrypts it in browser memory, independently checks the snapshot's record IDs, signed originals, frozen archive entries, printed batch membership, correction addenda and source before/after consistency.
4. The complete snapshot is reconstructed in **temporary in-memory objects**. SHA-256 fingerprints for source and reconstructed content must match.
5. A successful response lists recovered record, archive, frozen-original and correction counts. The application does not change, insert or delete any cloud/device record.
6. For negative tests, use a COPY of the encrypted file. A changed ciphertext or wrong passphrase must fail authentication. A backup with inconsistent signed originals must fail the recovery drill.

**A passing drill is not a full Supabase disaster recovery.** It does not recreate logins, RLS, storage buckets, database schema, edge functions or a new cloud provider; external cloud restoration remains an administrator-supervised later milestone.

## 4. Existing safeguards retained

- V2.9 daily private snapshots, manual snapshots and AES-256-GCM downloads remain available.
- Server-side restore is limited to **missing unsigned records**, following a preview and explicit confirmation. It does not overwrite existing records or signed/archived data, and it never recreates retired correction proposals.
- Signed endorsements, frozen flight originals and confirmed addenda must be preserved.
- Offline sync conflicts must still be resolved without silent overwrites.
- Neither backup health checking nor the isolated drill changes cloud data.
