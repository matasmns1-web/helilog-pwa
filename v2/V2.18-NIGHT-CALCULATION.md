# HeliLog V2.18 — UTC civil-twilight night time

**Release stage: TEST / `v2/development` only.** Production stays on V2.17 until the owner reviews this feature.

## Principle

For the EASA/SERA night definition, civil twilight ends when the **centre of the Sun is 6° below the horizon** in the evening, and starts when it rises through that threshold in the morning. The flight form uses the aerodrome reference-point coordinates and the recorded **UTC** date and off/on times; local time zones and summer-time transitions are not applied.

The built-in offline solar position implementation is based on approximate Meeus/SunCalc solar coordinates. For a flight between two different locations, HeliLog interpolates latitude/longitude along the straight line connecting the aerodrome reference points and tests the solar position at the midpoint of each recorded minute. The resulting number is **an estimate** rather than a published national AIP civil-twilight table or a recorded GPS trajectory.

## Form behavior

- **New flight:** automatic night calculation is on by default. Once date, UTC off/on times and both aerodrome positions are known, HeliLog fills `nightMin` and displays nearby civil dusk/dawn in UTC. It handles a normal next-day arrival if arrival time is earlier than departure time.
- **Known aerodromes:** EYVI, EYKA, EYPA, EYSA, EYKL, EYMO, EYKS, EYVK, EVRA, EETN and EPWA are bundled as WGS84 coordinate pairs. Sources: [OurAirports](https://ourairports.com/) facility data, verified October 2026, public-domain dataset.
- **Unknown operating site:** open **Departure and arrival coordinates (WGS84)** and enter decimal degrees; for circuits at the same site, the same position can be used for departure and arrival. Previously saved per-flight coordinates are reused for matching codes.
- **Missing or invalid coordinates:** the form shows why it cannot calculate and **blocks saving while automatic mode is on**. Uncheck the automatic toggle to enter night minutes manually.
- **Historical flights:** records saved before V2.18 open in manual mode and retain their existing `nightMin` value unless the pilot explicitly opts in to automatic calculation.
- **Archive history:** signed print archives stay immutable; proposing an amendment follows the existing correction workflow. No automatic edits to previous flights or archived pages.
- **Metadata:** each new/edited flight saves `nightCalculation` containing its mode (`automatic` or `manual`), the reference coordinates, the convention and algorithm. Flight `nightMin` stays the canonical value for totals, filters, PDF exports and synchronization.
- **Night take-offs and landings:** remain manual because detecting each take-off or landing time requires event timestamps that the current logbook does not collect.
- **Manual override:** deselect the automatic toggle, then edit `Night time (minutes)` and save. The pilot remains responsible for confirming official rules and AIP data.

## Known limitations and future improvements

- Only 11 bundled aerodromes for the initial private beta; manual coordinates support every other base, but there is no automatic global airport search yet.
- The straight-line interpolation is less suitable for very long routes, holding patterns, repeated circuits with a destination different from departure, or operations across national twilight rules.
- The astronomical model does not adjust for elevation/terrain, atmospheric refraction or national variations of the legal night definition.
- An entered departure and arrival place must each have WGS84 coordinates to calculate automatically. These are reference points, not real track data.
- Calculations use minute-midpoint resolution; differences of around a minute compared with official tables are possible. The app's output is an estimate; it is **not an independent EASA-certified method**.

## Acceptance tests

Run `node --test v2/v218-night-calculation.test.cjs` and the full staging regression suite. Manually check:

1. EYVI → EYVI, 19-10-2026, 09:00–10:10 UTC: 0 night min.
2. EYVI → EYVI, 19-10-2026, 22:10–23:40 UTC: 90 night min.
3. EYVI → EYVI, 19-10-2026, 14:30–18:00 UTC: mixed day/night.
4. EYVI → EYKA on the same date: different aerodrome coordinates and a labelled route estimate.
5. EYVI → EYVI, 19-10-2026, 23:45–00:30 UTC: 45 night min after midnight.
6. Unknown operating site: missing coordinate warning, manual coordinate entry, then auto result.
7. Edit a pre-V2.18 flight: preserved manual value; only an explicit toggle enables auto.
8. Toggle to manual, save an override, reload the flight and verify logbook/PDF/night totals.
9. Sync the edited record between two TEST devices and verify the same `nightCalculation` metadata.
10. Archived flights: only a proposed correction is allowed, never an in-place modification.

Production V2.17 is not modified by these changes.
