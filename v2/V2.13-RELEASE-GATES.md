# HeliLog V2.13 — Security, recovery, and main-branch promotion readiness

**Environment:** V2 test only. Two fictional pilot accounts. This is a risk review and release gate, **not** certification, pentesting or a production cutover.

## Verified on 19 October 2026

- **User acceptance:** 22/22 manual checks passed across two accounts, web, installed app, offline sync, logout and account switching (reported by owner).
- **Row isolation:** All six `public.helilog_*` tables have RLS. Authenticated pilots read their own rows; anonymous table SELECT was denied.
- **Write isolation:** A foreign-owner INSERT was rejected, and foreign-owner UPDATE and DELETE matched zero rows. The test transaction was rolled back; the temporary record left no trace.
- **Private RPCs:** Under a simulated second authenticated pilot, direct calls to `helilog_restore_preview` and `helilog_restore_missing_records` for the other account's snapshot were denied. An addendum and new print batch targeting the other account's archived flight were also denied. Own-account snapshot preview and backup health/retention were permitted. All RPC isolation probes were rolled back.
- **Backups:** A private manual snapshot was safely created for each test account. Two accounts now have backups. All seven server snapshots passed their stored SHA-256 digest checks. The scheduled backup cron job runs at 03:00 UTC and had succeeded in its latest reported runs. No existing snapshot was replaced or deleted.
- **App UI:** Previously loaded backup/restore status, cloud archive audit and cloud conflict previews are cleared when signing in to another account or signing out. In-flight backup operations check an account generation token before applying responses, downloads or restore prompts. New manual snapshots refresh account-scoped health and retention.

## Remaining gates before unrestricted real-user/production use

1. **Independent encrypted recovery:** On each pilot account, download a passphrase-encrypted snapshot, store it off-device, and use **Inspect encrypted backup** followed by **Run isolated recovery drill**. Record source/recovered fingerprint match. The test is browser-memory-only and is **not** proof of full disaster recovery after a Supabase outage.
2. **Privileged RPC review:** Seven necessary, authenticated-only `SECURITY DEFINER` routines still trigger Supabase's advisory warning. They use `auth.uid()` and owner-scoped data operations, and the tested cross-owner actions were denied, but require final detailed inspection/threat modeling before broad deployment. Do not blindly revoke their authenticated EXECUTE permissions: the backup/archive features require them.
3. **Authentication:** Supabase Auth's leaked-password check is still disabled; turn it on if available and audit password policy, rate limiting, redirect allowlist, recovery mail template and SMTP delivery. The six-character recovery-form minimum is a user preference, not the recommended password length.
4. **Privacy and support:** Provide a privacy notice (including medical details and signature data), retention and deletion procedures, feedback/contact and incident response process. The code is EASA-style, **not** an independently validated EASA-approved electronic logbook.
5. **Production infrastructure:** Create **separate production Supabase** project, apply and audit migrations, create independent backup/restore procedures and test signup. Do not reuse the disposable `HeliLog Test` project as production.
6. **Data migration:** Explicitly decide how to preserve V1 browser-local data and how to onboard pilot accounts to the new production database. No automatic copying or deleting of old browser data; current test sessions and fictional flights are **not** silently migrated.
7. **End-to-end acceptance:** Recheck account isolation, real email login/recovery, print/archive integrity, offline device updates, and encrypted independent restore on the final deployment URL.

## Proposed V1 → V2 cutover without data loss

- Preserve a read-only Git branch `archive/v1.43.2` pointing to today's original `main` state. Do not delete the production service or reset its persistent/browser data.
- Keep `v2/development` as the staging integration branch with mandatory GitHub regressions.
- Prepare a release PR **from the verified V2 tree** for `main`; never copy only the HTML file because the full JS modules, icons, manifest, service worker, migrations and tests are required.
- Production Render `helilog-pwa` currently uses **branch `main`, publish directory `.`**. V2 staging uses **branch `v2/development`, publish directory `v2`**. Merely merging commits into `main` does **not** switch the homepage to V2; a deliberate publish-directory change (or fully tested root-path packaging) is necessary.
- Before any Render cutover, verify PWA cache and relative asset paths at the final domain, configure the production Supabase publishable URL/key and Auth recovery redirect, and obtain a successful deployment rollback plan.
- Keep V1 deployment unaffected until production candidate checks pass and the owner approves the final switchover. If rollback is needed, restore the prior Render publish directory and archived commit; treat browser localStorage/service-worker domain differences explicitly.

No V1 production code, main branch, live records, signed history or cloud-backup tables are changed by this V2.13 stage.
