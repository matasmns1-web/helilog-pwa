# HeliLog V2.9 TEST — Backup & Recovery Acceptance

## Purpose

V2.9 adds scheduled account snapshots in the **HeliLog Test** Supabase project, checksum-protected private server backup history, passphrase-encrypted off-device downloads, and a **non-destructive, transactional missing-unsigned-record recovery**. It does NOT certify the logbook or replace professional managed database disaster recovery.

Only fictional test records and signatures should be used.

## Feature A — Automatic snapshots

- Database pg_cron job `helilog-v29-daily-test-snapshots` runs at **03:00 UTC daily** even if the browser or installed app is closed.
- It copies every account's cloud-record payloads and revisions, account metadata, immutable signed flight/endorsement print batches, frozen snapshots and signed correction addenda.
- Snapshots are SHA-256 verified and private to their owners through Row Level Security. App clients can **read only**; they cannot modify or delete snapshot rows.
- Server copies are kept within **the same Supabase project**. They are off-device, but NOT an independent backup if that project is lost, inaccessible or compromised.
- To create an additional snapshot immediately: **Profile → V2.9 Cloud backup & recovery → Backup now**. Use **Refresh backup history** to view recent copies.

## Feature B — Independent encrypted copy

1. On the TEST web site, sign in, open Profile and click **Refresh backup history**.
2. Select a snapshot in the dropdown. A daily or manual backup is suitable.
3. Enter a strong 12+-character passphrase twice. Click **Download encrypted backup**.
4. Store the resulting `HeliLog_V29_Encrypted_Cloud_Snapshot.json` in independent, secure storage and keep the passphrase separately. **HeliLog has no passphrase reset**.
5. Enter the passphrase under **Inspect encrypted backup**, select the saved file and verify the counts of cloud records, archives, frozen originals and signed addenda.
6. For a test of tampering, modify a COPY of that JSON's `ciphertext` and try inspection: AES-GCM authentication must reject it. Try a wrong passphrase; it must also fail.
7. Passphrase and plaintext are processed only by the user's browser; no third-party backup provider receives them. Encryption uses AES-256-GCM and PBKDF2-SHA256 with 310,000 iterations and random per-file salt/nonce.

**Important:** Encrypted external backup **inspection does not restore cloud data** in V2.9. Full recovery from a lost/empty provider or importing signed records requires a separate audited server-admin recovery operation and is not part of this release.

## Feature C — Guarded transactional restore (TEST only)

1. Choose an existing server snapshot and click **Preview safe restore**.
2. If all protected archive originals match and all existing mutable cloud records are unchanged, the preview reports the number of **missing unsigned** cloud records that can be reinserted.
3. If there are missing unsigned records, enter exactly `RESTORE MISSING RECORDS`, review the confirmation and choose **Restore missing records**.
4. The server checks the latest cloud fingerprint, verifies the selected snapshot again, saves a `pre_restore` snapshot and inserts missing unsigned rows **in one database transaction**.
5. Existing record revisions, signed endorsements, confirmed archive batches, frozen flight history and correction addenda are never overwritten, deleted, or rolled back. Retired flight correction proposals are never resurrected.
6. After a successful restore, resynchronize all devices before editing again.

A restore preview with zero missing records is expected on a healthy cloud account. **Do not delete test cloud records just to test recovery**; use automated tests or disposable records and a supervised test instead.

## Limits and later work

- Snapshots are held within Supabase and are not independently replicated to another provider; the user must keep independent encrypted downloads manually.
- Encrypted file import supports read-only inspection, not server restoration.
- Restore never rewinds, deletes, or overwrites existing records; conflicting versions require assisted review.
- This test implementation does not establish EASA/TKA-compliant signature identity assurance or full disaster-recovery capability.
- The scheduled task should be periodically checked for failed runs and growth/retention policy before real-world use.
