# HeliLog V2.8 — Archive Integrity, Backups & Recovery (Test)

**Test environment only:** https://helilog-v2-test.onrender.com. V1 production is unchanged. **Do not enter genuine flight histories, licence/medical information or real signatures.**

## Delivered in V2.8

- The Dashboard no longer displays the five Quick Actions cards (Add Flight, Import CSV, Endorsements, Backup, Print Archive). Their normal navigation and features remain intact.
- **Cloud account** no longer displays the old Local logbook protection card. When signed in, the **Cloud archive integrity → Verify archives** action examines the current cloud rows without editing them.
- Archive verification checks cloud batch IDs, page range continuity, frozen-entry references and recorded source snapshots, signed-endorsement sealing, and the relationship between confirmed corrections and their immutable originals.
- A device-local **SHA-256 evidence baseline** is saved only after a successful manual verification. Later checks detect modifications or disappearance of items this device previously verified. A new device has no pre-existing trusted baseline; hash equality alone is not an independently certified electronic signature.
- Before confirming a new flight/endorsement print batch or correction, HeliLog runs the cloud archive audit and refuses confirmation on failures. Proposed flight batches are also compared against the cloud's current original flight payloads. Server-side owner-checked Supabase RPCs remain authoritative.
- **Profile → Backup & restore → Download verified cloud recovery package** creates a user-initiated, SHA-256 protected JSON file after fresh synchronization and a passing cloud archive audit. It also checks the number of confirmed archive batches and corrections against this device's current copy.
- **Profile → Backup & restore → Inspect cloud recovery file** validates a V2.8 cloud recovery JSON's checksum, account association and expected structure without modifying local or cloud records.

## Key limitations

- **Backups are NOT automatic or off-device until the user saves the downloaded file somewhere independent.** The cloud database is not itself a proven disaster-recovery backup.
- The recovery package is **unencrypted JSON** and contains private pilot data and signatures. Save it securely, ideally in an encrypted location and in more than one copy. Do not share it or commit it to the public repository.
- **A cloud recovery file cannot be used to replace the live Supabase account in V2.8.** This is intentionally blocked; a transactional owner-verified restore, audit history and point-in-time recovery must be implemented and tested before enabling destructive restoration. Routine cloud-to-device download and sync remain supported through account sign-in.
- Offline unlocking, authenticated signing identity assurance, server-side independent immutable retention and scheduled backup automation require further work.
- SHA-256 proves the downloaded file has not changed since its checksum was computed; it does not prove the entries are authentic, correct, or approved by EASA/TKA.

## Acceptance test — use fictional records

1. Open the V2.8 TEST site and confirm the Dashboard Quick Actions cards and old Cloud Account protection panel are gone; Dashboard statistics and navigation remain.
2. Complete cloud synchronization, open Cloud account and press **Verify archives**. With your earlier fictional endorsement archive, expect a successful summary that includes its batch and frozen entry.
3. On the browser, create and sign one further fictional endorsement (or use one signed earlier); preview/print and confirm it via the standard web-only workflow. On the installed app, refresh and verify **Archived**. A new archive confirmation must require successful server-side integrity verification.
4. Return to the Cloud Account page, run the check again. Existing device evidence should remain accepted, with the new archive appended.
5. Open **Profile → Backup & restore**, download the verified cloud recovery package when cloud sync is complete, then save the file securely.
6. Choose **Inspect cloud recovery file** and select that file. Check that SHA-256 and the record counts are accepted, and that nothing was restored.
7. Test a **copy of the file**, not your only backup: deliberately change one fictional record in the JSON without updating the checksum. Inspection must reject the file. Cloud and device data must remain unaffected.
8. Test on the other device while the web archive status is synchronized. Ensure the existing signing, search, flight editing and print archive workflows still work.

## Failure handling

If verification fails or recovery-file inspection is rejected, **do not reset browser storage, remove the app or force upload records**. Keep the original devices intact, download a separate unmodified safety copy when possible, and preserve printed originals. Failures should stop new archive confirmations until the discrepancy is resolved.

## Further work after V2.8

- Add recoverable encrypted off-device backups with schedules, retention, verified restore drills and audited rollback.
- Implement transactional cloud-account restoration with no silent loss of existing frozen originals or signatures.
- Perform server-side archive snapshot provenance validation and multi-device interrupted-write/rotation tests.
- Final security, availability, offline-access and EASA regulatory reviews before allowing real operational use.
